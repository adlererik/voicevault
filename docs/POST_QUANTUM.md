# Hybrid call establishment

VoiceVault v2 uses X25519 plus ML-KEM-768 for every new call. The aim is to protect captured voice traffic if an attacker can later break the recorded X25519 exchange. The phone and telecommunications links may already be controlled by an NSA-class adversary when the call is made. The design relies on trusted endpoints, verified contacts and sound authentication at that time. Active quantum-era impersonation and supply-chain attacks are outside this model. Earlier classical-only recordings retain the security of their original exchange. [Threat model](THREAT_MODEL.md)

ML-KEM-768 is the owner's explicit exception to the preference to avoid NIST algorithms. The project pins `libcrux-ml-kem` 0.0.11 with the `mlkem768` feature and calls its portable Rust API on both native and Cortex-M33 paths. ML-KEM lets the responder create a shared 32-byte secret using the initiator's fresh encapsulation key. Only the initiator's matching decapsulation key can recover that secret from the ciphertext, under the ML-KEM security assumptions. [FIPS 203](https://csrc.nist.gov/pubs/fips/203/final) · [libcrux implementation](https://docs.rs/libcrux-ml-kem/0.0.11/libcrux_ml_kem/)

## Protocol and wire format

The fixed suite is `Noise_KKhfs_25519+MLKEM768_ChaChaPoly_BLAKE2s`. It uses Snow 0.10's implementation of the experimental Noise hybrid forward secrecy modifier. The HFS draft describes the transform as unofficial and unstable. VoiceVault follows the modifier rules implemented by Snow, including placement of the initiator's KEM public key after the first DH operation. This is a synchronous protocol between pinned devices. Signal's asynchronous PQXDH is a separate construction. [Noise HFS draft](https://raw.githubusercontent.com/noiseprotocol/noise_hfs_spec/master/noise_hfs.md) · [Noise revision 34](https://noiseprotocol.org/noise_rev34.html) · [Signal PQXDH](https://signal.org/docs/specifications/pqxdh/)

| Flight | Noise processing order | Wire bytes |
|---|---|---:|
| Initiator → responder | Ephemeral X25519 public key, `es`, encrypted 1,184-byte ML-KEM public key, `ss`, authenticated empty payload | 1,248 |
| Responder → initiator | Ephemeral X25519 public key, `ee`, encrypted 1,088-byte ML-KEM ciphertext, KEM secret mixed into the chaining key, `se`, authenticated empty payload | 1,152 |

Both pinned static X25519 public keys enter Noise as premessages. The protocol name binds the algorithm suite. The prologue uses the `VoiceVault hybrid call v2` domain, both verified Ed25519 public keys in initiator/responder order, a context-presence byte and the 32-byte accepted-invitation context when present. Native calls always bind the verified offer and acceptance. Noise authenticates the prologue and exchange through the transcript hash and handshake tags. Noise mixes each DH output and the KEM output into its chaining key and derives separate transport keys for the two directions. The final responder tag checks that both sides derived compatible hybrid secret state. Encrypted Confirm and Ready plus local consent gate audio on each endpoint.

Each endpoint obtains four 32-byte blocks from its trusted entropy interface before constructing a call handshake. One supplies the X25519 ephemeral. Two supply the ML-KEM key generation seed and one supplies encapsulation randomness. Each role uses its required KEM input once and clears the unused input when the handshake is dropped. The initiator creates an ephemeral ML-KEM keypair per call. The responder uses fresh encapsulation randomness per call. There is no algorithm negotiation, resumption or classical call path. Incorrect role, length, message order or authentication poisons the handshake state. If either flight is withheld, the call cannot start. Enrollment continues to use classical Noise XX with independently compared fingerprints, so authentication must hold when the session is established.

The two flights use 39 and 36 fragments on the lab link, each with at most 32 payload bytes. The six-byte header contains the `0xd2` startup marker, the flight number, the total flight length as a little-endian 16-bit value, the fragment index and the fragment count. An endpoint accepts one expected startup flight at a time, with fixed storage, a three-second deadline and a 96-datagram assembly budget. The native path also applies the existing per-tick radio budget. Active audio retains the 128-byte ChaCha20-Poly1305 record and 20 ms slot profile. An observer can see startup length, call timing, traffic direction and routing metadata. A hostile phone can deny delivery.

## What is erased

Seed owners clear their bytes on consumption and drop. The initiator's owned 2,400-byte ML-KEM private key is cleared when the handshake is split, fails or is dropped. The adapter and Snow clear owned shared-secret, DH, chaining-key, HMAC and HKDF working buffers. The transport keys live in separate zeroizing cipher objects. Closing a call or reaching the five-minute media epoch retires those objects, and the next call needs fresh keys. The implementation does not persist session secrets.

The design relies on erasure for forward secrecy against later endpoint compromise. Compiler-generated copies, libcrux and other primitive internals, registers, OS crash artifacts and physical memory remnants need separate review. Extracting a live media key can expose the records protected by that key. Within-call key-exposure containment is a separate design problem.

## Verification and hardware fit

The lab checks all 80 ML-KEM-768 cases selected from the pinned NIST ACVP key generation and encapsulation/decapsulation publications. The checks include known answers for implicit rejection and invalid keys. An independent test implementation of the Noise key schedule compares both hybrid flights, the transcript hash and both directional transport keys through encrypted control records. It shares the selected cryptographic primitives with the implementation. The existing Cacophony KK and XX cases still check the classical primitives and enrollment wiring.

Attack tests include genuine legacy KK downgrade messages, changed identities sharing a DH key, mismatched invitations, wrong message order, every byte position in both flights, cross-call replay, unavailable entropy, and malformed KEM material sent by an authenticated peer. A five-process scenario alters a KEM fragment through a confined phone worker and verifies that both audio paths stay closed. The new fuzz campaigns reach the authenticated KEM adapter and bounded startup parser. A fifth Kani harness checks the two-flight completion gate under its encoded bound. [Source and test mapping](SECURITY_CONTROLS.md)

The linked `no_std` Cortex-M33 diagnostic runs the hybrid exchange, its startup fragmentation and the encrypted Opus pipeline in QEMU under the STM32U585-class capacity budget. The probe includes both endpoint crypto states and uses public test secrets. Real-board timing, interrupt stack, secure-element integration and physical leakage remain hardware validation tasks. [Platform measurements and limits](PLATFORM.md)

The local Snow patch registers the KEM name, bounds KEM scratch arrays and clears owned secret buffers. It preserves the existing HFS token order and Noise key schedule. The libcrux-platform patch removes libc from bare-metal dependency resolution. The lab reverses these patches and compares the resulting files with pinned upstream hashes. [Patch verification](../scripts/check_crypto_vendor.py)

Before deployment, independent review must cover the HFS construction, local suite integration, key confirmation, native and Cortex-M33 machine code, and the actual erasure boundary. Passing a test vector or observing a stack watermark establishes the tested result under its stated conditions.
