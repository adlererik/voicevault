# Quietlink Lab threat model

The trusted side consists of the supervisor's synthetic local UI, the two endpoint processes, and their implementation and dependencies. The supervisor provides public contact records and the expected signer keys over separate local control datagrams that the phones and relay never inherit. Each endpoint generates its signing and static DH secrets locally. The host OS, launcher, dynamic loader, and executable before seccomp installation are part of the trusted computing base.

The two phones and relay can see the direction, timing, size, and public counters of ciphertext records, as well as link framing and call start and stop. They can cooperate, drop or withhold all traffic, or substitute, duplicate, reorder, delay, and corrupt datagrams. They cannot grant consent through the media interface. The virtual tests exercise these faults against the same endpoint state, record parser, reassembler, and Opus wrapper used in the wall-clock run. The wall-clock tests exercise real process boundaries and actual nonblocking kernel backpressure. Availability and resistance to traffic analysis beyond the fixed active-slot record size are outside the guarantee.

## Pairing, calls, and record handling

The contact record holds a 32-byte Ed25519 verifying key, a separate 32-byte X25519 public key, and a 64-byte Ed25519 signature over both keys with a contact-specific domain. Verify the signature against the expected out-of-band signer before creating a pin. In a hardware deployment the independent identity verification step would need an authenticated physical or human channel.

Noise KK uses a call-specific prologue and the pinned static keys. Snow generates OS-random ephemeral keys for each wall-clock call. The deterministic scenarios use named fixture seeds. The two Noise handshake messages have empty payloads. Each direction uses its own Noise split key in stateless transport. The first eight wire bytes are the little-endian nonce sequence. The remaining 120 bytes carry a 104-byte encrypted body and 16-byte tag. The body has a type, a length, bounded payload, and zero padding. Changing the public counter changes the AEAD nonce and invalidates the tag.

Encrypted sequence 0 confirms local consent. Sequence 1 acknowledges that both confirmations are in place. Media starts at sequence 2 and follows the absolute slot number, allowing gaps. Send and receive state use one shared 64-slot replay policy per incoming direction with separate state for each call. Unauthenticated input, out-of-range media, and unsupported commands cannot advance the replay window. Opus payload framing and duration checks run after authentication. Startup control traffic withheld or delivered out of order causes the call to fail. Recovery after a failed start or process reset requires a new handshake.

## Linux worker policy

The Linux x86-64 forwarder starts with an empty environment. It uses connected nonblocking Unix datagram sockets on descriptors 0 and 1. The launcher sets a finite kernel send buffer. Before polling, the child closes descriptors 2 and above, enables `PR_SET_NO_NEW_PRIVS`, installs a default-EPERM seccomp BPF policy, and runs escape probes. Failure stops forwarding and the endpoint startup times out. The filter checks the x86-64 audit architecture and matches exact syscall numbers, including the absence of the x32 ABI bit.

The allowed operations are `poll`, `clock_gettime`, `rt_sigreturn`, `exit`, `exit_group`, and connected `sendto` / `recvfrom`. The last two are restricted to descriptors 0 and 1, null address pointers, zero flags, and at most 39 bytes including the receiver's oversize sentinel. Other operations, including file open, `socket`, `connect`, `ptrace`, `process_vm_readv`, descriptor duplication, and ancillary descriptor transfer, receive EPERM. The test checks the denies against a live endpoint process and verifies that a probe still crosses its two inherited sockets. Worker startup and its kernel/loader rely on the trusted executable. Arbitrary hostile code can consume CPU within the host's scheduler policy. Endpoint work stays bounded per slot, and blocked IPC remains nonblocking. [Linux seccomp filter documentation](https://www.kernel.org/doc/html/latest/userspace-api/seccomp_filter.html)

## Audio and validation scope

The endpoint profile is mono Opus at 16 kHz, 320 samples per slot, 24 kbit/s CBR, no FEC, and DTX disabled. Encoded silence uses the same 60-byte Opus packet budget. Mute and encoder underrun use encrypted filler. Fragments carry at most 32 bytes of a record, with at most eight incomplete assemblies and a three-tick lifetime. The receive jitter buffer has eight positions and nominal four-slot playout delay. It uses Opus PLC for missing or malformed frames and outputs silence for authenticated filler. A scheduling gap can drop playout ticks, leaving zero samples at those positions in the WAV.

The harness exercises the published Cacophony KK vector through Snow's handshake and both directions of stateless split transport. Decoder conformance checks all 12 RFC 8251 vectors with the upstream quality comparator at the lab output rate and channel count, accepting either of the two RFC reference decodes as the upstream harness does. The vector harness exercises valid Opus modes and geometries beyond the narrower wire profile. Kani checks the actual replay bitmap and bounded call-state transitions. Snow, Opus, the kernel and the full process graph are exercised by the runtime tests. [Noise test-vector format](https://github.com/noiseprotocol/noise_wiki/wiki/Test-vectors) · [Opus test vectors](https://opus-codec.org/testvectors/)

Separate hardware validation would measure worst-case MCU timing and memory with real capture, playback, and interrupt loads. It would test BLE MTU negotiation, connection intervals, fragmentation, RF retries, reconnect behavior, and observable radio timing. Acoustic work would measure microphone and speaker leakage, mute behavior, echo paths, and the device's power and RF side channels. The software lab reports digital playout timing and synthetic WAV direction only.
